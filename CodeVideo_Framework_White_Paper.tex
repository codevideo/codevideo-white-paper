\section{Introduction}

The rapid growth of online education has transformed the software learning experience, creating unprecedented demand for high-quality, interactive software courses. As the demand for instructional video content continues to rise, so do the demands for editing, structuring, and delivering this content at scale is a process that is both resource-intensive and technically challenging.

In this document, we present \textit{CodeVideo}, an event-sourcing-based framework designed to streamline the creation and management of software instructional videos. By simulating every interaction (keystrokes and or mouse interactions) in an Integrated Development Environment (IDE), the framework can produce deterministic, repeatable sequences that simulate a live coding session. The result is not only the ability to generate a static snapshot of the IDE state at any given time but also the capability to generate entire instructional videos programmatically, ensuring consistency and precision across sessions.

\section{CodeVideo Framework Architecture and Abstraction Layers}

The CodeVideo Framework represents a modular and highly abstracted approach to IDE-based video course creation. This section provides an in-depth look at its primary abstractions and the structured hierarchy that enables reproducible, fine-grained state control over IDE interactions. The three main components are Courses, Lessons, and Actions.

\subsection{Course}

At the topmost level of the \textit{CodeVideo} framework, we define a course, \( C \), represented by:

\begin{itemize}
    \item A unique identifier, \( C_{id} \)
    \item A descriptive name, \( C_{name} \)
    \item A sequence of instructional units or lessons, \( L = \{ L_1, L_2, \dots, L_n \} \)
\end{itemize}

\subsection{Lesson}

Each lesson, \( L \), is composed of:
\begin{itemize}
    \item An (optional) initial state snapshot of the project workspace, \( S_{initial} \). A null or empty initial state represents a completely empty IDE
    \item A sequence of discrete actions \( A = \{ a_1, a_2, \dots, a_m \} \)
    \item An (optional) final state snapshot \( S_{final} \) that serves as the baseline for subsequent lessons
\end{itemize}

\subsection{Action}

Central to the framework is the concept of an \textit{action}, the smallest unit of interaction within the IDE. Actions, represented as \( a_i \), encode the following elements:

\begin{align*}
    a_i : \text{action\_type} \rightarrow \text{action\_value}
\end{align*}

Examples of action types include text entry commands, cursor movements, file modifications, and verbal narration. For instance:

\begin{itemize}
    \item \textbf{Editor Typing Action:} 
    \begin{align*}
        & a_{type} = \text{``editor-type''} \\
        & a_{value} = \text{``console.log(`Hello, world!');''}
    \end{align*}
    \item \textbf{Terminal Typing Action:} 
    \begin{align*}
        & a_{type} = \text{``terminal-type''} \\
        & a_{value} = \text{``npm run start''}
    \end{align*}
    \item \textbf{File Explorer File Creation Action:} 
    \begin{align*}
        & a_{type} = \text{``file-explorer-create-file''} \\
        & a_{value} = \text{``mytextfile.txt''}
    \end{align*}
    \item \textbf{Narration Action:} 
    \begin{align*}
        & a_{type} = \text{``author-speak-before''} \\
        & a_{value} = \text{``I'm going to log a message to the console.''}
    \end{align*}
\end{itemize}

It should also be noted that formally a series of actions n actions can be broken down into n lessons, given that the lesson captures the snapshot defined by the previous actions. For example, consider 100 actions that represents a rather long lesson. We can break this lesson into two lessons of 50 actions each, as long as the snapshot of the IDE at the end of the first lesson is the same as the snapshot of the IDE at the start of the second lesson.

\begin{align*}
    S_{final}(L_1) = S_{initial}(L_2) = S_{initial}(L_1) + a_{1} + a_{2} + \dots + a_{50}
\end{align*}

\section{Actions in Detail}

Actions form the entire foundation of the CodeVideo framework. From an abstract standpoint, an action should be able to handle any basic interaction that is possible with a computer. There are limited ways of interacting with a computer, in order of most common to least common:

\begin{itemize}
    \item Keyboard: A keyboard has a large variety of keys, but they can be broken down into 3 categories: letters, numbers, and symbols.
    \item Mouse: a mouse has motion sensor, 3 buttons, and a scroll wheel.
    \item Trackpad: which have 1 button and a touch surface.
    \item Audio inputs (microphones), which represent a series of points at varying amplitudes.
    \item Video inputs (cameras), which represent a series of images.
\end{itemize}

We abstract these inputs to three main categories of actions: keyboard, mouse, and multimedia (audio and video).

Within an IDE, there are then 3 target locations where these actions can be applied: the editor, the file tree, and the terminal.

\subsection{Anatomy of an Action Name}

An action name is formulated by the following schema:

\texttt{<domain>-<action-type>}

Where:

\begin{itemize}
    \item \textbf{Domain} refers to the domain of the action (e.g., editor, author, file-explorer, terminal, external, slide).
    \item \textbf{Action Type} describes the specific action being performed (e.g., type, click, speak).
\end{itemize}

Note that the domains need not be specifically related to an IDE. The CodeVideo framework supports browser previews of websites (the `external' domain), as well as slide presentations (the `slide' domain).

\subsection{Action Composition}

Actions are strictly composed of two parts: the action type and the action value. The action type is a string that describes the action, and the action value is a string that represents the value of the action. For example, an editor typing action would have the action type of ``type-editor" and the action value of ``console.log('Hello, world!');".

\subsection{Action Granularity}

The framework implements a hierarchical action granularity system, where the base unit of interaction can be configured according to course requirements:

\begin{itemize}
    \item \textbf{Atomic Actions} (Default): The finest level of granularity, capturing:
    \begin{itemize}
        \item Individual keystrokes: \( a_{key} = \{key: `a', step: n\} \)
        \item Single cursor movements: \( a_{cursor} = \{position: (x,y), step: n\} \)
        \item Mouse events: \( a_{mouse} = \{type: 'click', position: (x,y), step: n\} \)
    \end{itemize}
    \item \textbf{Composed Actions}: Higher-level abstractions that can be configured:
    \begin{itemize}
        \item Line-level changes: \( a_{line} = \{content: string, lineNumber: n\} \)
        \item Block-level modifications: \( a_{block} = \{content: string, range: (start, end)\} \)
        \item Semantic operations: \( a_{semantic} = \{type: `function-declaration', content: string\} \)
    \end{itemize}
\end{itemize}

The granularity level can be adjusted dynamically, with the framework maintaining the atomic actions internally while presenting a more abstract interface when desired:

\[
A_{composed} = f(a_1, a_2, ..., a_n) \text{ where } a_i \text{ are atomic actions}
\]

\subsection{Composite Actions}

Composite Actions are a highly composed actions that represent, and can be broken down into singular, atomic actions. Composite actions can manifest in two ways:

\begin{enumerate}
    \item Via a more complex `value': while the action name becomes simpler, the action value becomes more complex. For example, the ``composite-mouse" action is an abstracted action for an entire mouse movement, including the mouse's x and y coordinates, timestamp, what buttons were clicked, and so on.
    \item Via a series of actions: for example the `composite-file-explorer-create-file-via-mouse' action is a composite action that represents a series of actions: moving to the file explorer, right-clicking the file explorer, moving the mouse to the `New File...' option, clicking that option, typing in the new file name, and hitting enter.
\end{enumerate}

In both cases, these composite actions can be broken down into their respective atomic actions as needed. The key trigger is the starting `composite-' prefix in the action name. Other composite action examples include:

\begin{itemize}
    \item \textbf{composite-mouse}: represents the sequence of atomic actions to perform a full mouse interaction sequence (movements, clicks, scrolls) over a defined time period.
    \item \textbf{composite-file-explorer-create-file-with-mouse}: represents the sequence of atomic actions to perform the entire process of creating a new file using mouse interactions.
    \item \textbf{composite-file-explorer-create-file-with-terminal}: represents the sequence of atomic actions to perform creating a new file using terminal commands
    \item \textbf{composite-file-explorer-create-folder-with-mouse}: represents the sequence of atomic actions to perform the entire process of creating a new folder using mouse interactions.
    \item \textbf{composite-file-explorer-create-folder-with-terminal}: represents the sequence of atomic actions to perform creating a new folder using terminal commands
    \item \textbf{composite-file-explorer-collapse-all-folders-with-mouse}: represents the sequence of atomic actions to perform collapsing all expanded folders in the file explorer using mouse interactions.
    \item \textbf{composite-file-explorer-collapse-all-folders-with-keyboard}: represents the sequence of atomic actions to perform collapsing all expanded folders in the file explorer using keyboard shortcuts.
    \item \textbf{composite-terminal-run-command}: represents the sequence of atomic actions to perform executing a command in the terminal, including typing the command and pressing enter.
    \item \textbf{composite-editor-refactor-variable-name}: represents the sequence of atomic actions to perform renaming a variable throughout the codebase, involving multiple find-and-replace actions.
    \item \textbf{composite-file-explorer-move-file-with-mouse}: represents the sequence of atomic actions to perform moving a file from one directory to another using mouse interactions.
    \item \textbf{composite-file-explorer-move-file-with-terminal}: represents the sequence of atomic actions to perform moving a file from one directory to another using terminal commands.
    \item \textbf{composite-editor-close-all-tabs-with-mouse}: represents the sequence of atomic actions to perform closing all open editor tabs using mouse interactions.
    \item \textbf{composite-editor-close-all-tabs-with-keyboard}: represents the sequence of atomic actions to perform closing all open editor tabs using keyboard shortcuts.
    \item \textbf{composite-editor-open-n-terminals-with-mouse}: represents the sequence of atomic actions to perform opening multiple terminal instances using mouse interactions.
    \item \textbf{composite-editor-open-n-terminals-with-keyboard}: represents the sequence of atomic actions to perform opening multiple terminal instances using keyboard shortcuts.
\end{itemize}

\section{Snapshots: Capturing the Full IDE State}
\label{sec:snapshots}

Snapshots represent the entire state of the IDE at a given point, allowing for precise rollback and reproducibility:
\begin{align*}
    S = \langle & \text{metadata},\\
    & \text{file\_structure},\\
    & \text{selected\_file},\\
    & \text{open\_files},\\
    & \text{editor\_content},\\
    & \text{caret\_position},\\
    & \text{terminal\_content},\\
    & \text{mouse\_position}
    \rangle
\end{align*}

Where:

\begin{itemize}
    \item \textbf{Metadata} contains high-level course information.
    \item \textbf{File Structure} denotes the directory tree visible in the IDE.
    \item \textbf{Selected File} and \textbf{Open Files} track active files.
    \item \textbf{Editor Content} and \textbf{Caret Position} record the current text and cursor position.
    \item \textbf{Terminal Content} contains the current command-line output.
    \item \textbf{Mouse Position} contains the current mouse coordinates.
\end{itemize}

\subsection{Reconstitution of IDE State}

In a software lesson, the authors, keyboard, and mouse components can all be used in parallel while creating lesson, much like how a real software developer would interact with an IDE. The IDE then, is the more or less linear result of these interactions. The IDE state can be reconstituted by replaying the actions in the same order they were recorded. We use logical time to represent the start of any one of these ``parallel" actions, and let the renderers handle the overlapping complexity.

\section{Validators: Deterministic Quality Assurance}

Each lesson’s continuity is verified through a \textit{snapshot validator}, to confirm that the content of the given project at the end of one lesson matches the initial state of the next lesson:

\[
\forall i \in [1, n-1], \quad S_{final}(L_i) = S_{initial}(L_{i+1})
\]

If any two consecutive snapshots do not match, the validator throws an error, ensuring seamless progression across lessons.

\section{Renderers: Virtual Editors and CodeVideo Studio}

The CodeVideo framework integrates a \textit{GUI IDE} with a \textit{virtual IDE}, which emulates IDE interactions in a standalone environment:

\begin{itemize}
    \item The virtual editor provides snapshots on demand via \( getProjectSnapshot() \), allowing course authors to generate real-time previews of each state.
\end{itemize}

The rendering engine, \textit{CodeVideo Studio} (https://studio.codevideo.io), provides a visual representation within the IDE, enabling authors to edit actions dynamically and validate course accuracy.

\section{Generators: Converting Courses, Lessons, and Actions into a Variety of Multimedia Formats}

\subsection{Parallel Video Generation}
\label{sec:parallel}

Because a lesson is an ordered list of actions, its video can be rendered in pieces and joined. The joins are invisible only if two conditions hold. Every piece must place each action on exactly the frame an uninterrupted render would use, and every piece must start from exactly the screen an uninterrupted render would show at that frame. \textit{CodeVideo} satisfies both conditions in an experimental \textit{deterministic} render mode. Realtime screen capture remains the default.

\paragraph{Deterministic time.} In deterministic mode the browser runs on a virtual clock. Timers, animation frames, the date and performance clocks, and CSS animations advance only when the renderer steps the clock, one frame of $1000/60$ milliseconds at a time. Pending work settles before each capture, so frame $f$ always shows the state at virtual time $\tau(f) = 1000f/60$ ms, regardless of how long the capture takes. A single \textit{planning pass} plays the lesson once on this clock and records the exact time of every action, mouse path and speech cue.

\paragraph{Render checkpoints.} The snapshot $S$ of Section~\ref{sec:snapshots} describes logical state, which replaying the actions reconstitutes exactly ($S_n = S_{n-1} + a_n$). It does not determine the picture. The same files and terminal output can appear with a different editor scroll position or selection, with a menu open, or with a scrollbar halfway through fading out. During planning the renderer therefore saves \textit{render checkpoints} taken from the running editor instead of derived from $S$:

\[
C_k = \langle S_k, V_k, \kappa_k, t_k \rangle
\]

Where:

\begin{itemize}
    \item \(S_k\) is the logical IDE state, as in Section~\ref{sec:snapshots}.
    \item \(V_k\) is the presentation state: each tab's editor scroll position and selections, the layout, open menus, dialogs and text inputs, slide overlays, the mouse position and target, and the time remaining on transitions such as a fading scrollbar or the terminal caret.
    \item \(\kappa_k\) is the execution cursor: the next action and, inside a typing or wait action, the character offset, the step within that character, any typo awaiting correction and the absolute deadline of the current wait.
    \item \(t_k\) is the absolute virtual time.
\end{itemize}

Checkpoints are offered at every action boundary and, inside typing and wait actions, at most once per 500 ms of virtual time. One is saved only when nothing is in motion: no mouse movement or CSS animation may be in flight. Points inside actions matter because a single action can dominate a lesson. The Short Video of Appendix~\ref{app:performance} spends 15 of its 29 seconds in one typing action, and mid-action points raise its checkpoints from 13 to 56. Each checkpoint carries a fingerprint of the project, render settings and seed, plus a checksum, and a worker refuses any checkpoint that does not match.

\paragraph{Addressable randomness.} Mouse paths, typing cadence and optional typos are random but seeded. Instead of drawing from one sequential stream, each choice comes from a generator seeded by its own coordinates:

\[
r = \mathrm{PRNG}\big(H(\mathit{seed}, \ell, i, o, p)\big)
\]

where \(\ell\) is the lesson, \(i\) the action index, \(o\) the character offset within a typing action (omitted for other actions) and \(p\) the purpose of the draw, such as a mouse curve, a delay, or whether to make a typo. Here \(H\) is the FNV-1a hash and PRNG the Mulberry32 generator. A worker that resumes at character \(o\) therefore makes the same choices as one that typed every earlier character, and no choice depends on how the video is split.

\paragraph{Segments.} With \(W\) workers, the renderer cuts the timeline at checkpoints into at most \(W\) contiguous, half-open frame ranges \([f_j, f_{j+1})\). A checkpoint at virtual time \(t\) opens its range at frame \(\lceil 60t/1000 \rceil\). Cuts are chosen to minimize the longest range:

\[
\min_{\text{cuts}} \; \max_{j} \; (f_{j+1} - f_j)
\]

Each worker restores its checkpoint, starts the clock at \(t_k\) on the same global frame grid, renders its range and stops at the next cut. Its action, mouse and speech events must match the planning trace, or the job fails. The encoded segments are concatenated in frame order without re-encoding. Narration is mixed once over the planning timeline, so speech that crosses a cut remains a single cue. When there are fewer checkpoints than workers, fewer workers run.

Segments follow the machine rather than the action list. In our measurements each worker spent roughly 4 to 13 seconds starting a browser and editor, at least as long as a typical action, so a few balanced segments cost far less than one worker per action.

In our tests, renders with one, two, four and eight workers produce bit-identical source frames and identical event traces. On our test machine the fastest configurations render the Short Video 2.11 times faster than realtime capture (four workers) and the Long Video 3.66 times faster (eight workers). Appendix~\ref{app:performance} gives the measurements and their limits.

\subsection{Temporal Abstract Syntax Tree Management}

Central to the framework's refactoring capabilities is the concept of a Temporal Abstract Syntax Tree (TAST), which extends traditional AST manipulation to include logical time as a dimension. Simply described, this is the abstract syntax tree after every moment (action) in time. The concept of TASTs are not new, and have been explored in various works \cite{moore2022temporal}.

\subsubsection{Formal Definition}

A Temporal AST node at logical step \(n\) is defined as:

\[
TAST_{node}(n) = \langle ID, Type, Value(n), Children(n), Metadata(n) \rangle
\]

Where:
\begin{itemize}
    \item \(ID\) is a unique identifier persisting across the action sequence
    \item \(Type\) represents the node type (e.g., Identifier, FunctionDeclaration)
    \item \(Value(n)\) is the node's value at step \(n\)
    \item \(Children(n)\) represents child nodes at step \(n\)
    \item \(Metadata(n)\) stores additional information like scope and references
\end{itemize}

When performing retrospective modifications (e.g., variable renaming), the framework uses a forward propagation algorithm:

\[
\forall m > n: TAST(m) = Apply(TAST(m-1), Modification(n))
\]

The modification propagation follows these principles:

\begin{enumerate}
    \item \textbf{Identity Preservation}: Node identities remain constant across the sequence, enabling tracking of elements despite name changes:
    \[
    ID(TAST_{node}(n)) = ID(TAST_{node}(m)) \quad \forall n,m
    \]
    
    \item \textbf{Reference Integrity}: All references to modified nodes are updated while maintaining semantic correctness:
    \[
    Refs(TAST_{node}(m)) = UpdateRefs(Refs(TAST_{node}(n)), Modification(n))
    \]
    
    \item \textbf{Scope Resolution}: Modifications respect lexical scoping rules across the logical sequence:
    \[
    Scope(TAST_{node}(m)) = ResolveScope(Scope(TAST_{node}(n)), Environment(m))
    \]
\end{enumerate}

\subsubsection{Implementation Strategy}

The framework implements temporal AST modifications through a combination of:

\begin{itemize}
    \item Forward replay with modification injection
    \item Lazy evaluation of affected subtrees
    \item Cached intermediate states for performance optimization
\end{itemize}

This approach enables complex refactoring operations while maintaining the integrity of the recorded action sequence. For example, when renaming a variable at step \(n\), the system:

\begin{enumerate}
    \item Captures the modification intent: \(M = \{type: "rename", target: ID, newValue: name\}\)
    \item Identifies all subsequent steps containing references to the target: \(Steps_{affected} = \{m | m \geq n \land HasRef(TAST(m), ID)\}\)
    \item Applies the modification across all affected steps while preserving other concurrent modifications
\end{enumerate}

\section{Applications For Extremely High Quality Dataset Generation For Use in Large Language Models}

A large component of context missing from large language models and transformers is exactly the contextual travel-through-time data that CodeVideo catalogs. By including the full, correct, and complete steps to creating software, either through the array of actions or a TAST to LLM training data, we can provide a more comprehensive dataset for coding training data. CodeVideo could be used as an invaluable tool in synthetic data generation for large language models.

\section{Conclusion}

The \textit{CodeVideo} framework offers a robust, reproducible method for generating IDE-based educational content, reducing manual editing and increasing course consistency. With its event-sourcing architecture, the framework not only captures precise IDE states but also provides a platform for creating interactive, context-rich software engineering tutorials.

\section{Measured Performance of Parallel Video Generation}
\label{app:performance}

This appendix compares the deterministic parallel renderer of Section~\ref{sec:parallel} with realtime capture, the default renderer. Every figure is the wall-clock time of a complete render, from the command-line start to a finished MP4 file.

\subsection{Method}

All measurements were taken on one machine: an Apple M3 Max with 16 logical CPUs and 64~GiB of memory, running macOS and Node.js 23.11. Each render produces 1920$\times$1080 video at 60 frames per second from a fixed seed, without narration or web previews. Two example lessons were rendered:

\begin{itemize}
    \item \textbf{Short Video}: 14 actions that create and open a file, type into it for 15 seconds, scroll, type a terminal command and finish on a slide. Its timeline is 28.65 seconds, or 1,719 frames.
    \item \textbf{Long Video}: 87 actions that build a small TypeScript task tracker from an empty folder. It types 4,541 characters into five files and runs seven terminal commands, with scrolling and two slides. Its timeline is 4 minutes 57 seconds, or 17,837 frames.
\end{itemize}

Realtime capture plays the lesson in one browser while recording the screen, then transcodes the recording to MP4. The deterministic renderer captures each frame as a JPEG at quality 92 and encodes with software H.264 (libx264, CRF 18) through FFmpeg. The pipelines differ, so the comparison measures throughput rather than equal image quality. Short Video times are medians of three runs. Long Video times are single runs.

\subsection{Scaling}

Render time grows linearly with video length. Predictions made from the Short Video before the Long Video was rendered came within 4 seconds of every checkpoint result. The speed-up still improves with length, because fixed costs such as browser start-up are spread over more frames. Table~\ref{tab:marginal-cost} gives the marginal cost of each extra second of video,

\[
m = \frac{T_{\mathrm{Long}} - T_{\mathrm{Short}}}{D_{\mathrm{Long}} - D_{\mathrm{Short}}}
\]

where \(T\) is render time and \(D\) is video duration. Realtime capture costs 1.10 seconds per second of video. Dividing that by a configuration's marginal cost gives the speed-up the configuration approaches on very long videos.

    \hline
    \textbf{Workers} & \textbf{Seconds per second of video} & \textbf{Limit vs realtime} \\
    \hline
    1 & 0.93 & 1.2$\times$ \\
    2 & 0.55 & 2.0$\times$ \\
    4 & 0.33 & 3.3$\times$ \\

    \caption{Marginal cost of the checkpoint renderer and the implied speed-up limit on the test machine.}
    \label{tab:marginal-cost}
\end{longtable}

Three costs keep the speed-up below the worker count:

\begin{itemize}
    \item \textbf{Planning.} The planning pass is serial: 5--6 seconds for the Short Video and about 25 seconds for the Long Video. Saving checkpoints adds little. With its 620 checkpoints, the Long Video's planning took 23.6--26.9 seconds, against 23.1--26.1 seconds for planning without checkpoints.
    \item \textbf{Start-up.} Each worker launches a browser and loads the editor. On the Short Video the slowest worker needed 3.7 seconds when running alone, 5.8 seconds with four workers and 10.6 seconds when eight started together. That contention makes eight workers slower than four on the Short Video. On the Long Video the cost is amortized, and eight workers win (92.2 seconds against 109.2).
    \item \textbf{The longest segment.} With checkpoints only at action boundaries, nothing could cut the Short Video's 15-second typing action, so its largest segment at four workers was 903 frames. Mid-action checkpoints cut that action at characters 57 and 245 and the terminal command at character 6, leaving segments of 450, 450, 450 and 369 frames. The four-worker render fell from 26.0 seconds, measured with the same harness the day before, to 19.3 seconds.
\end{itemize}

Without checkpoints, extra workers pay to replay the beginning of the lesson. In the \textit{sequential seek} variant, each worker replays the lesson from the start on the virtual clock and captures only its own range. On the Long Video with eight workers, sequential seek evaluates 142,696 frames instead of 17,837 and takes 151.1 seconds, 64\% longer than checkpoints. Its best result is 135.8 seconds, at four workers.

\subsection{Verification}

\begin{itemize}
    \item For each lesson, renders with one, two, four and eight workers have identical SHA-256 hashes for every source frame and identical event traces. Each output has exactly the expected frame count, with no missing or repeated frames.
    \item Across all segments, checkpoint workers capture each frame exactly once, so the frames evaluated equal the frames output.
    \item Mid-action checkpoints change no output. With typos and jitter off, the Short Video matches a render that uses action-boundary checkpoints only, frame for frame.
    \item With typos and jitter on, every deterministic render of the Short Video, from one to eight workers and with or without checkpoints, produced identical frames and traces. Random choices do not depend on how the video is split.
\end{itemize}

\subsection{Limits}

\begin{itemize}
    \item Identical output assumes the same browser build, fonts, renderer build, lesson and seed. Results across different browsers, operating systems or font rasterizers are not promised.
    \item Different worker counts change the H.264 segment boundaries, so encoded MP4 files can differ byte for byte even when every source frame is identical.
    % Remove this item if the difference is fixed before publication.
    \item The two deterministic strategies are not yet pixel-identical to each other. On the Long Video, checkpoints and sequential seek differ in 97 of 17,837 frames, in faint antialiasing around the mouse cursor.
    % If the rename-input mismatch is still open at publication, add:
    % \item One restoration test that resumes while a file-rename input is on screen still renders a slightly different glyph.
    \item Lessons with external web previews cannot be checkpointed, because the external page's state cannot be saved. They fall back to sequential seek.
    \item All figures come from one Apple Silicon machine. Linux servers have not been measured.
\end{itemize}
